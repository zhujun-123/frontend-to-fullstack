## 问题与系统不变量

一个 Goroutine 可能同时等待结果、超时和取消。select 必须保证一次只提交一个通信操作；多个 Channel 同时参与时要以一致锁顺序避免死锁；未被选中的等待节点必须清理，否则会重复唤醒或泄漏。

## 前端认知起点

`Promise.race([work, timeout])` 可以帮助理解“多个候选中先处理一个”。Go 需要更细地思考：每个 Case 是发送还是接收，Channel 是否 nil/关闭，选中一次后其他生产者是否仍在运行，以及取消信号由谁传播。

## 最小心智模型

1. 先求值所有 Channel 与发送表达式。
2. 随机化 Case 的轮询顺序，减少长期固定偏置。
3. 按 Channel 地址排序得到稳定加锁顺序。
4. 第一轮查找已就绪通信；没有就绪且有 default，立即执行 default。
5. 需要阻塞时，把当前 G 以多个 `sudog` 节点加入相关等待队列并 park。
6. 某个 Case 唤醒后，清理其他 Channel 上未选中的等待节点。

## Go 1.26.5 当前实现

`runtime.selectgo` 为 Case 生成 `pollorder` 和 `lockorder`。轮询顺序采用伪随机排列；锁顺序按 Channel 排序，保证多个 select 即使 Case 顺序不同也不会反向加锁。准备阻塞时，一个 G 会对应多个等待节点，但最终只有一个 Case 获胜。

nil Channel 的 Case 永远不就绪，因此常用把 Channel 设为 nil 动态禁用分支。已关闭 Channel 的接收立即就绪并返回零值与 `ok=false`；向已关闭 Channel 发送会 panic。

## 类比成立范围

- 都能组合业务结果、超时和取消。
- 都要求处理“输掉的任务是否还在继续”。
- 都不能用单次先后现象推断稳定优先级。

## 类比失效边界

- `Promise.race` 返回第一个 settled Promise；select 只提交一次可执行 Channel 通信。
- select 不自动取消其他 Goroutine，也不消费其他 Channel 的结果。
- 多个 Case 同时就绪时采用伪随机选择，不按源码从上到下保证优先级。
- `default` 会把阻塞等待变成轮询；放在紧循环中可能造成 CPU Busy Loop。

```bash
cd examples/go-runtime
```

正常实验验证 nil Case 被禁用、就绪 Channel 被选择、Context 取消能结束等待。错误边界实验验证关闭 Channel 立即就绪，调用方必须检查 `ok`，否则零值可能被误当成真实结果。

## 真实生产故障场景

一个 Worker 使用 `select { case job := <-jobs: ... default: }` 放在无休眠循环中，希望“提高吞吐”。当队列为空时它占满 CPU；队列关闭后又没有检查 `ok`，开始无限处理零值 Job。故障同时表现为 CPU 高、日志暴增和无效下游请求。

## 常见错误与版本变化

- 接收表达式必须使用 `value, ok := <-ch` 处理关闭边界。
- nil Channel 可禁用 Case，但如果所有 Case 都是 nil 且没有 default，select 永久阻塞。
- `time.After` 在高频循环中会创建 Timer；可复用 Timer 时要正确 Stop/Reset。
- Go 1.23 起 Timer Channel 对外同步，未引用且未停止的 Timer 可被 GC 回收，`Stop`/`Reset` 后不会再收到旧值；旧教程中的 Drain 模式要结合模块 Go 版本判断。
- 不要用 Case 源码顺序表达优先级，需要优先级时拆成两阶段选择或显式队列。
