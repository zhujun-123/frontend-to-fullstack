## 问题与系统不变量

对象必须至少活到最后一次使用，不能因为函数返回就丢失；高频分配又不能每次都争抢全局锁或直接向操作系统申请页面。分配器要同时保证生命周期正确、对齐正确、GC 可扫描，并把常见小对象路径做得足够便宜。

## 前端认知起点

前端已经会问“谁还引用这个对象”“哪条交互路径持续产生临时对象”。这些问题可以直接迁移。新增的一步是：Go 编译器可能证明对象只需活在当前调用栈，也可能因为返回、闭包、接口或无法证明生命周期而让它逃逸到堆。

## 最小心智模型

| 层级 | 大白话 | 主要作用 |
| --- | --- | --- |
| Goroutine Stack | 当前任务随身工作台 | 调用返回后容易复用，分配便宜，可增长 |
| `mcache` | P 的本地小件货架 | 常见小对象快速分配，减少锁竞争 |
| `mcentral` | 某个 Size Class 的共享仓库 | 给 mcache 补充 Span |
| `mheap` | Runtime 的页面与 Span 总仓 | 管理大对象和向 OS 获取的内存 |

## Go 1.26.5 当前实现

编译器先做逃逸分析，决定某个值是否能安全留在 Goroutine 栈上。堆分配再按大小与是否包含指针选择路径：极小且不含指针的对象可走 Tiny Allocator；常见小对象映射到 Size Class，从当前 P 的 `mcache` 对应 Span 取槽位；缓存不足时向 `mcentral` 获取 Span；更大的对象直接由 `mheap` 管理。

Size Class 的意义不是“对象大小必须刚好匹配”，而是用少量固定规格换取快速定位和批量管理。代价是内部碎片：例如请求大小落入更大的规格，没用到的空间也被占用。

Goroutine 栈可增长和搬移，Runtime 会修正栈中指针；这与把每个系统线程预留一块固定大栈的模型不同。

## 类比成立范围

- Chrome Allocation Timeline 与 Go `alloc_space` 都适合找“谁持续制造对象”。
- Heap Snapshot Retainer 与 Go `inuse_space` 调用图都帮助定位“谁还持有对象”。
- 预分配 Array 容量与预分配 Slice 容量都能减少扩容复制。

## 类比失效边界

- JavaScript 开发者通常不能选择对象留在栈还是堆；Go 编译器会做逃逸决策。
- 返回指针不等于永远逃逸，内联和跨函数分析可能改变结果。
- `new(T)` 不等于堆分配，字面量也不等于栈分配。
- Heap Profile 不等于进程 RSS；Runtime 保留页、栈、代码、mmap 和内核记账都会造成差异。

## 可运行实验

```bash
cd examples/go-runtime
go test ./labs/memory
go test -bench=. -benchmem ./labs/memory
go test -gcflags='all=-m=2' ./labs/memory
```

正常现象：预分配容量的版本分配次数低于逐步增长版本。它只验证同版本同机器的趋势，不设置固定纳秒阈值。错误边界：看到 `escapes to heap` 不代表必须优化，必须先证明它处于热点路径。

实验服务可以观察一段有上限的分配前后 `MemStats`：

```bash
go run ./cmd/labserver
curl 'http://127.0.0.1:8080/work/allocate?count=512&size=4096'
```

## 真实生产故障场景

JSON 接口每次请求都把未知大小结果追加到 Slice，再转成 `map[string]any` 做二次编码。流量上升后 `alloc_space` 显示编码与 Slice 扩容占主导，GC CPU 同步增加。修复点可能是预估容量、减少中间结构或流式编码，而不是盲目调大 `GOGC`。

## 证据与排查

| 证据 | 用法 | 结论边界 |
| --- | --- | --- |
| `-gcflags='all=-m=2'` | 看逃逸原因和内联 | 编译器线索，不是性能结论 |
| `go test -benchmem` | 对比 `B/op`、`allocs/op` | 只比较同环境趋势 |
| Heap `alloc_space` | 累计分配热点 | 适合看分配速率 |
| Heap `inuse_space` | 采样时仍存活内存 | 适合看持有和泄漏 |
| `runtime/metrics` | Heap、对象数、Size Class 趋势 | 需要与请求量和 GC 周期对齐 |
| RSS / 容器内存 | 进程实际压力 | 不能直接等同 HeapAlloc |

## 常见错误与版本变化

- 不要用“指针在堆、值在栈”作为规则。
- `sync.Pool` 是跨 GC 周期可被清空的临时对象复用池，不是缓存或对象生命周期管理器。
- 过度对象池化可能增加引用存活、清零成本和复杂度，先用 Profile 证明价值。
- Go 1.22 改变循环变量生命周期，修复大量闭包捕获陷阱；阅读旧逃逸案例时要确认版本。
- Runtime Size Class 和内部结构不是语言兼容性承诺，文章源码固定到 go1.26.5。
