## 问题与系统不变量

并发任务需要交换数据，但共享内存直接读写容易产生数据竞争。Channel 必须保证元素不被凭空复制或丢失、关闭状态可被观察、等待者能被唤醒，并且发送接收建立 Go Memory Model 定义的同步关系。

## 前端认知起点

前端常见的 MessageChannel、事件队列和 Stream 都有生产者消费者影子。可迁移的是“生产速度和消费速度需要协调”；不能迁移的是“发送永不阻塞”以及“关闭只是移除监听器”。

## 最小心智模型

Channel 有三条主要路径：

1. 已有接收者等待：发送方把值直接交给接收方。
2. 有缓冲且未满：值进入环形缓冲区。
3. 无接收者且缓冲已满：发送方以 `sudog` 节点进入发送等待队列并挂起。

## Go 1.26.5 当前实现

`runtime.hchan` 保存元素数量 `qcount`、容量 `dataqsiz`、缓冲区指针 `buf`、发送/接收索引、`sendq`、`recvq`、关闭标记和锁。缓冲 Channel 使用环形队列；等待发送或接收的 G 通过 `sudog` 挂接在队列上。

Runtime 源码维护的重要不变量包括：通常 `sendq` 与 `recvq` 至少一个为空；缓冲区有数据时不应还有接收等待者，缓冲区未满时不应还有发送等待者。锁保护 `hchan` 字段和相关等待节点，但 Runtime 不会在持锁时直接切换另一个 G 的状态，以避免与栈收缩死锁。

关闭 Channel 会唤醒等待者：接收方在缓冲耗尽后得到元素零值和 `ok=false`，发送方则因向已关闭 Channel 发送而 panic。

## 类比成立范围

- 都能把生产者与消费者解耦。
- 缓冲容量都能吸收短时速率差。
- 取消订阅和 Context 取消都提醒我们管理生命周期。

## 类比失效边界

- Channel 不是 Kafka、Redis Stream 或持久化队列；进程退出后数据消失。
- Channel 默认不是广播。一个值通常只会被一个接收者取走。
- 缓冲区不是吞吐魔法，只是改变阻塞发生的位置。
- 关闭是发送方的责任；接收方随意关闭会与其他发送者竞态。
- `nil` Channel 的发送和接收永久阻塞，可用于动态禁用 `select` 分支，但误用会泄漏。

## 真实生产故障场景

请求处理启动三个 Pipeline 阶段，客户端断开后最后一级停止接收，但上游仍向无缓冲 Channel 发送。请求日志已经结束，Goroutine 数量却持续上涨；数小时后内存和调度延迟一起恶化。

## 证据与排查

| 证据 | 重点 |
| --- | --- |
| Goroutine Dump | `chan send`、`chan receive` 栈是否大量重复，创建者在哪里 |
| Block Profile | 哪个 Channel 操作累计阻塞时间最高 |
| Trace | 哪些 G 被阻塞、由谁唤醒、Context 取消后是否退出 |
| 指标 | 队列长度、生产/消费速率、丢弃数、Goroutine 数 |
| 日志 | 任务 ID、入队、出队、关闭、取消原因；不要记录每个元素造成日志风暴 |

排查时先确认 Channel 的所有者：谁创建、谁发送、谁关闭、消费者何时停止。没有这四个答案，单纯增大 Buffer 通常只是延后故障。

## 常见错误与版本变化

- 向已关闭 Channel 发送会 panic；从已关闭且已排空 Channel 接收立即返回零值和 `ok=false`。
- `for value := range ch` 只有在 Channel 关闭后才结束。
- 多个发送者存在时，通常由协调者在所有发送者结束后统一关闭。
- Go 1.23 起 Timer Channel 对外表现为同步 Channel，`cap` 和 `len` 为 0，并保证 `Stop`/`Reset` 后不再收到旧值；Runtime 内部缓冲属于实现细节。
- 不要通过 `len(ch)` 做并发正确性判断，读取后状态就可能变化。
