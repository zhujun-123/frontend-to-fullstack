## 问题与系统不变量

两个 Goroutine 同时访问同一变量，只要至少一个是写且没有同步，就存在数据竞争。CPU、编译器和 Runtime 都可以在规范允许范围内重排或缓存操作；“本地测试总是先写后读”不是可见性保证。

## 前端认知起点

前端单线程主执行环境让很多共享 Store 更新天然串行，Web Worker 又通常通过消息复制隔离。Go Handler、后台任务和定时器可能在不同系统线程上同时访问同一对象，因此不可变风格只能改善设计，不能替代锁、Channel 或 Atomic 发布。

## 最小心智模型

先确定共享状态的不变量，再选同步原语：

| 状态形态 | 优先选择 | 原因 |
| --- | --- | --- |
| 多字段必须一起变化 | Mutex | 临界区内原子地维护业务不变量 |
| 单调计数、标志、单个指针 | Atomic | 无锁读写一个独立状态 |
| 不可变配置整体替换 | `atomic.Pointer[T]` | 构建新快照后一次发布 |
| 所有权随消息转移 | Channel | 让单一 Goroutine 维护状态 |

## Go 1.26.5 当前实现

`sync.Mutex` 公共类型封装 `internal/sync.Mutex`。无竞争时通过 CAS 走快速路径；竞争时可能短暂自旋，随后借助 Runtime 信号量挂起等待者。正常模式追求吞吐，等待超过阈值的场景可进入饥饿模式，把所有权直接交给队首等待者以控制尾延迟。

Memory Model 保证一次 `Unlock` 同步先于之后成功的 `Lock`；类型化 Atomic 操作按顺序一致语义参与全局顺序。Atomic 只保证该次原子操作，不自动保护“余额减少 + 流水追加”这类多字段事务。

## 类比成立范围

- 不可变快照适合读多写少的配置发布。
- Redux Reducer 的“先定义状态转换”有助于缩小锁内逻辑。
- Web Worker 消息所有权与 Channel Owner 模式都减少共享写。

## 类比失效边界

- JavaScript 主线程上的顺序执行不能迁移成 Go 的并发安全保证。
- Atomic Counter 不能推广为任意无锁数据结构。
- `RWMutex` 不是读多就必然更快，读临界区长度和写竞争决定结果。
- Channel 也不是所有共享状态问题的答案；强行把简单计数变成专用 Goroutine 会增加生命周期和排队成本。

## 可运行实验

```bash
cd examples/go-runtime
go test ./labs/synclab
go test -race ./labs/synclab
go test -bench=. -benchmem ./labs/synclab
```

正常实验让 16 个 Goroutine 同时累加，Mutex 与 Atomic 都保持最终计数。Benchmark 只比较当前机器竞争模式下的趋势，不能得出“Atomic 永远更快”。错误边界可临时把计数改成普通 `value++` 再运行 Race Detector，观察两条冲突调用栈；不要把故意 Race 代码保留在默认测试。

## 真实生产故障场景

限流器用普通 Map 保存租户计数，一个 Goroutine 定期重置，Handler 同时递增。Race 导致计数丢失，偶尔还触发并发 Map Fatal。换成 Atomic 只能保护单个计数，如果“当前窗口 + 计数 + 过期时间”必须一致，仍需要 Mutex 或不可变窗口快照。

## 证据与排查

| 证据 | 重点 |
| --- | --- |
| `go test -race` | 冲突读写栈、Goroutine 创建栈 |
| Mutex Profile | 累计等待时间最高的锁 |
| Block Profile | 锁、Channel、Cond 等阻塞位置 |
| Trace | 锁等待与调度、下游延迟的时间关系 |
| Goroutine Dump | 大量 G 是否卡在同一 `Lock` |
| 业务日志/指标 | 临界区 Key、队列深度、冲突率；不要在持锁时慢日志 |

## 常见错误与版本变化

- Mutex 零值可用，但首次使用后不能复制；`go vet` 的 copylocks 检查有价值。
- 锁内调用未知回调、网络、日志或阻塞 Channel 容易放大尾延迟和死锁风险。
- Atomic 发布指针前必须先完整构造不可变对象，发布后不能再无锁修改其字段。
- 失败的 `TryLock` 不建立 happens-before，循环 TryLock 也可能变成忙等。
- Go 1.25 新增 `WaitGroup.Go`，减少 `Add` 与启动 Goroutine 的时序错误；WaitGroup 仍不是错误收集或取消工具。
