## 问题与系统不变量

系统线程创建和切换昂贵，但服务端可能同时存在成千上万个等待网络、锁、定时器或 CPU 的任务。调度器必须始终守住三个不变量：可运行的 Goroutine 最终能获得执行机会；阻塞一个任务不应冻结同一进程的其他任务；同时执行 Go 代码的并行度受 `GOMAXPROCS` 约束。

## 前端认知起点

| 前端认知 | 可以迁移 | 不能照搬 |
| --- | --- | --- |
| Event Loop | 任务需要排队并等待执行机会 | Go 不是单线程回调循环 |
| Web Worker | 多核可以真正并行 | Goroutine 默认共享地址空间，没有 Worker 隔离 |
| Task / Microtask Queue | 队列影响任务何时运行 | Go 没有 Promise Microtask 的同等优先级规则 |

## 最小心智模型

把 G 看成待办任务，M 看成真正干活的系统线程，P 看成运行 Go 代码所需的工位。M 必须拿到 P 才能执行 Go 代码，P 保存本地运行队列和 `mcache` 等资源。

## Go 1.26.5 当前实现

1. `go fn()` 创建 G，并优先放入当前 P 的本地运行队列。
2. M 持有 P，从本地队列取 G；必要时检查全局队列、Netpoll，或从其他 P 偷取一部分任务。
3. G 在 Channel、Mutex、网络 I/O 等位置等待时会被挂起，M 可以继续运行其他 G。
4. M 进入长时间系统调用时，P 可以与它分离并交给另一个 M，避免 P 上的任务一起停住。
5. `sysmon` 等运行时机制参与网络轮询、系统调用监控和抢占。函数调用安全点与异步抢占共同避免纯计算任务长期独占执行资源。

本地队列减少所有任务争抢一个中央锁，Work Stealing 用来处理 P 之间的负载不均。具体取队列顺序属于实现细节，不能依赖它保证业务先后顺序。

## 类比成立范围

- Event Loop 和 GMP 都要回答“当前不能执行的任务放在哪里、何时继续”。
- Web Worker 和多个 P 都能帮助理解多核并行。
- 浏览器 Performance Timeline 与 Go Trace 都能展示任务执行、等待和唤醒。

## 类比失效边界

- P 不是 CPU，也不是线程；它是运行 Go 代码所需的一组逻辑资源。
- Goroutine 不是 Promise。G 只有执行状态，没有内置结果、错误和取消。
- Goroutine 可以在线程之间迁移，因此不能用线程局部认知推断它下一次在哪里运行。
- 调度公平不等于业务顺序。需要顺序时应显式使用队列、锁或协议。

## 可运行实验

```bash
cd examples/go-runtime
go test ./labs/scheduler
go test -run TestRunCPUWorkCompletesAllTasks -trace scheduler.trace ./labs/scheduler
go tool trace scheduler.trace
go test -bench=. -benchmem ./labs/scheduler
```

正常现象：测试能在 `GOMAXPROCS=2` 下完成全部有界任务；Trace 能看到多个 Goroutine 的创建、运行和等待。错误边界：不要断言某个 Goroutine 必须先运行，调度顺序本身不稳定。

也可以启动实验服务后制造有限 CPU 工作：

```bash
go run ./cmd/labserver
curl 'http://127.0.0.1:8080/work/cpu?tasks=32&iterations=1000000'
```

## 真实生产故障场景

一个接口为每条数据无上限启动 Goroutine，下游连接池只有 50 个连接。请求量上升后，大量 G 堆积在连接获取和 Channel 发送上，内存上涨、P99 延迟恶化，CPU 却不一定满。根因不是“GMP 太慢”，而是并发没有与下游容量对齐。

## 证据与排查

| 证据 | 看什么 | 能回答什么 |
| --- | --- | --- |
| `go tool trace` | Goroutine 状态、调度延迟、阻塞位置 | 时间花在运行、等待还是调度 |
| Goroutine Profile | 相同栈大量重复、创建来源 | 是否泄漏或无上限扇出 |
| Block / Mutex Profile | Channel、锁等待热点 | 哪个同步点在排队 |
| `/sched/goroutines:goroutines` | Goroutine 总量趋势 | 是否持续增长不回落 |
| `/sched/latencies:seconds` | 可运行到获得 CPU 的延迟分布 | 是否存在调度压力 |
| CPU Profile | 热函数与 Runtime 占比 | 是业务计算、锁竞争还是调度开销 |

先把业务请求时间线与 Profile 时间窗对齐，再解释 Runtime 指标；单看 Goroutine 数量不能证明泄漏。

## 常见错误与版本变化

- `GOMAXPROCS` 限制同时执行 Go 代码的 P 数量，不限制 Goroutine 数量。
- `runtime.NumGoroutine()` 只有总数，没有创建栈和等待原因。
- Go 1.22 起，`for` 循环变量按每次迭代重新创建，并支持对整数 `range`；旧版闭包捕获结论要标注版本。
- Go 1.25 新增 `WaitGroup.Go`，减少 `Add` 与 `go` 顺序写错的机会，但它仍不传播返回值或错误。
- Goroutine 很轻不等于免费；栈、引用对象、连接、日志和调度都需要预算。
