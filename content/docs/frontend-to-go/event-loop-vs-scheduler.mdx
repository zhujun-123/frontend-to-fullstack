## 共同抽象：谁来决定下一段代码何时执行

前端开发者熟悉调用栈、任务队列和微任务队列。JavaScript 运行时在当前调用栈清空后，继续处理排队任务。

Go 中也存在调度，但调度单位变成了 Goroutine。运行时会把大量 Goroutine 分配到可用的执行资源上。

## 类比成立的部分

- 都不需要业务代码直接管理每一次底层线程切换。
- 阻塞当前执行资源会影响其他任务获得执行机会。
- 都需要理解任务排队、调度时机和长任务影响。

## 类比失效的部分

- JavaScript 回调通常在同一事件循环线程中依次运行；Go 的 Goroutine 可能在不同线程上运行。
- JavaScript 普通对象很少遇到多线程同时写；Go 的共享内存可能产生真实的数据竞争。
- Goroutine 调度并不承诺固定顺序，不能依赖“先启动就先完成”。

## 前端开发者最容易踩的坑

把 Goroutine 当作“不需要关心并发安全的异步回调”。一旦多个 Goroutine 读写同一份数据，就需要通过 Channel、Mutex、Atomic 或所有权边界保证正确性。
