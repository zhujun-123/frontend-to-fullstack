## 问题与系统不变量

如果每个等待网络数据的连接都长期占住一个系统线程，连接数上升会迅速消耗线程、栈和切换成本。Netpoll 必须在 I/O 暂不可用时安全挂起对应 G，并在就绪、Deadline、关闭或错误发生时只唤醒正确的读写等待者。

## 前端认知起点

Node.js/libuv 也把 Socket 注册到 epoll/kqueue 等机制，收到就绪事件后推进任务。Go 的迁移重点是：业务仍可写同步阻塞风格的 `Read`/`Write`，Runtime 在下面把等待转换成 Goroutine park 和 ready。

## 最小心智模型

<Mermaid
  chart={`flowchart LR
    G[G calls Conn.Read] --> NB[Non-blocking syscall]

`pollDesc` 分别跟踪读和写等待者，并保存关闭状态、序列号与读写 Deadline Timer。序列号用于避免文件描述符关闭复用后的旧事件错误唤醒新连接。

## Go 1.26.5 当前实现

`internal/poll` 与 Runtime Netpoll 协作。Socket 被设置为非阻塞并注册到平台 Poller：Linux 使用 epoll，Darwin/BSD 使用 kqueue。读写遇到暂不可用时，当前 G 通过 `pollDesc` 的读或写信号量 park；Poller 返回就绪事件后，Runtime 把相应 G 放回可运行队列。

Deadline 由 `pollDesc` 中的 Timer 参与，在到期时解除等待并返回超时错误。关闭连接也会发布关闭状态并唤醒等待者。Netpoll 只负责 I/O 就绪与唤醒，真正执行 Go 代码仍由 GMP 调度器完成。

## 类比成立范围

- libuv 和 Netpoll 都使用操作系统就绪通知承载大量 Socket。
- 前端 Abort/Timeout 与 Go Context/Deadline 都要沿请求链传播。
- 浏览器 Network Timing 与 Go `httptrace` 都能拆 DNS、连接、TLS 和首字节时间。

## 类比失效边界

- Netpoll 不是运行 JavaScript Callback 的 Event Loop，也不是唯一的 Go 调度器。
- 不是所有阻塞都能被 Netpoll 接管：普通文件、某些系统调用、cgo 和特定 DNS 路径可能阻塞系统线程。
- Socket 就绪不等于完整业务消息已到达；应用协议仍要处理半包、EOF 和长度边界。
- 一个连接一个 Goroutine 很常见，但仍必须限制连接、请求和下游并发总量。

## 可运行实验

```bash
cd examples/go-runtime
go test ./labs/netpoll
go test -race ./labs/netpoll
go test -bench=. -benchmem ./labs/netpoll
```

正常实验在 `127.0.0.1` 建立真实 TCP Listener，完成有边界的 Echo Round Trip。错误边界实验使用已取消 Context，确认 Dial 不会无限等待。Benchmark 每次创建连接，主要用于观察趋势，不代表连接复用后的 HTTP 性能。

## 真实生产故障场景

HTTP Client 没有总超时，连接池又允许大量等待。下游发生半开连接后，数千个 Goroutine 堆在网络读取；CPU 不高，但请求 P99、Goroutine 数和文件描述符持续上涨。Netpoll 正常工作并不意味着业务有正确 Deadline。

## 常见错误与版本变化

- 只有 `http.Client.Timeout`、Transport 各阶段超时和 Context 共同设计，才能形成完整时间预算。
- 忘记关闭 HTTP Response Body 会阻碍连接复用并增加 FD/连接压力。
- `Read` 返回 `n > 0` 时可以同时返回非 nil error，调用方应先处理已读数据再处理错误。
- epoll/kqueue 是平台实现；Windows 使用不同机制，不能把 Linux 细节写成跨平台语言保证。
- Go Runtime Netpoll 内部结构持续演进，本文源码固定到 go1.26.5，公共行为以 `net` 契约为准。
