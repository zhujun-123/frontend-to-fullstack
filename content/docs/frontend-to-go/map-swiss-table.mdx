## 问题与系统不变量

Map 要把任意可比较 Key 映射到 Value。哈希冲突一定会发生，因此查找必须继续探测并最终用 Key 比较确认；删除不能错误截断后续探测；增长和迭代还要遵守语言规范对新增、修改和删除元素的要求。

## 前端认知起点

JavaScript `Map` 能直接迁移 Key-Value、缺失检查和迭代概念。`Object` 更像属性集合，并带有原型、字符串/Symbol Key 等额外语义。Go Map 的 Key 类型在编译期固定，读取缺失 Key 返回 Value 零值，需要 comma-ok 区分。

## 最小心智模型

Go 1.26.5 的 Group 包含 8 个 Key/Value Slot 和一个 8 字节控制字。哈希被拆成 H1 与 H2：H1 用于选择 Table 和探测起点，H2 存在控制字中，用位运算一次筛出 Group 内可能匹配的槽位，再做真实 Key 比较。

## Go 1.26.5 当前实现

小 Map 在不超过 8 个元素时可直接使用一个 Group。更大的 Map 由 Directory 指向一个或多个 Table；每个 Table 是开放寻址 Swiss Table，使用二次探测。控制字区分空、已删除 Tombstone 和已占用槽位，并保存已占用 Key 哈希的低 7 位。

单个 Table 先扩容，达到实现上限后分裂为两个 Table；Directory 使用可扩展哈希的高位索引 Table。这样增长只重排一部分 Map，而不是一次搬迁全部数据。

迭代顺序未指定且实现会随机化。迭代期间删除尚未访问项则不应返回；修改项应返回最新值；新增项可能出现也可能不出现。

## 类比成立范围

- JS Map 与 Go Map 都适合动态 Key-Value 查找。
- 两者都需要区分“Key 不存在”和“Value 恰好为空/零值”。
- 预估容量都能减少增长和重排成本。

## 类比失效边界

- Go Map 的 Key 必须可比较，Slice、Map 和 Function 不能直接作为 Key。
- Go Map 迭代顺序不稳定，不能用它做排序或协议输出保证。
- 普通 Go Map 不支持并发读写；前端单线程状态对象的经验不能证明服务端并发安全。
- Go 1.24 之前常见的 `hmap/bmap`、Bucket 与 Overflow Bucket 文章属于历史实现，不是 1.26.5 当前结构。

## 可运行实验

```bash
cd examples/go-runtime
go test ./labs/maplab
go test -bench=. -benchmem ./labs/maplab
```

正常实验使用 comma-ok 区分“存在且值为 0”和“不存在”。错误边界实验验证读取 nil Map 返回零值，但写 nil Map 会 panic。Benchmark 只验证当前环境查找趋势，不用固定性能阈值证明复杂度。

## 真实生产故障场景

一个进程级配置 Map 被后台刷新 Goroutine 更新，同时多个 HTTP Handler 读取。低流量时看似正常，压力上来后 Race Detector 报告读写竞争，生产可能直接出现 `concurrent map read and map write`。修复需要明确快照替换、Mutex、`atomic.Pointer` 或 `sync.Map` 的适用模型，而不是重试。

## 常见错误与版本变化

- `value := m[key]` 不能区分缺失和零值，必要时使用 `value, ok := m[key]`。
- nil Map 可以读和删，不能写；`make` 或字面量才能得到可写 Map。
- 删除迭代中的元素受规范支持，但新增项是否被访问不确定。
- Go 1.24 将 Map 实现改为 Swiss Table；旧 Bucket 图只能标注为 Go 1.23 及更早历史。
- `sync.Map` 针对写一次读多次或不同 Goroutine 操作不相交 Key 等特定模式，不是普通 Map 的无脑替代。
