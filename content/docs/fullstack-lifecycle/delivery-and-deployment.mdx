## 工具不是同一层

| 工具 | 解决的问题 | 不负责什么 |
| --- | --- | --- |
| Jenkins / GitHub Actions | 自动执行测试、构建和发布步骤 | 不直接定义应用如何运行 |
| Docker | 封装程序和运行依赖，生成镜像 | 不负责多实例调度 |
| 镜像仓库 | 保存带版本的镜像 | 不负责运行服务 |
| Kubernetes | 维持实例数量、网络、健康和滚动更新 | 不负责生成源码制品 |
| Helm | 参数化和版本化 Kubernetes 配置 | 不替代 Kubernetes |

Jenkinsfile 的价值不只是“执行几个命令”，而是把交付过程写成可审查、可重复的代码。

## Docker 的第一性原理

“在我电脑上能运行”无法证明生产环境也能运行。Docker 镜像把二进制、依赖和启动方式封装为同一份不可变制品。

镜像需要：

- 使用明确版本的基础镜像。
- 多阶段构建，减少运行镜像体积。
- 不把密码和生产配置写入镜像。
- 使用提交 SHA 或语义版本作为镜像标签。
- 记录构建来源和依赖信息。

## Kubernetes 维护期望状态

你声明需要三个实例，Kubernetes 尝试让现实状态不断接近期望状态。它还需要知道：

- 应用是否启动完成：Readiness Probe。
- 应用是否仍然存活：Liveness Probe。
- 使用哪个镜像和配置。
- 如何暴露网络。
- 如何滚动更新以及允许多少不可用实例。

## 发布完成不等于流水线变绿

真正的发布完成标准包括：

- 新实例使用了预期镜像。
- 健康检查通过。
- 真实请求可以完成。
- 错误率、延迟和资源指标没有异常。
- 数据库迁移兼容新旧版本。
- 回滚命令、目标版本和停止条件明确。

## 完成标准

- 能从生产实例追溯到镜像、流水线和 Git 提交。
- 同一镜像可以在测试和生产环境运行，差异由配置注入。
- 发布过程包含自动测试、健康验证和观察窗口。
- 数据库迁移不会让旧版本立即失效。
- 能在不重新构建代码的情况下回滚到上一个镜像。
