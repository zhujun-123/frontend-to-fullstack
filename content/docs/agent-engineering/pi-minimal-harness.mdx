## 最小 Harness 到底需要什么

去掉品牌和界面，一个可工作的 Coding Agent 只需要形成闭环：

```text
用户消息 → 模型 → 工具请求 → 工具执行 → 工具结果 → 模型
```

但“只写一个 while 循环”仍然不够。工程实现至少需要处理：流式事件、工具参数、取消、错误、会话历史、不同模型协议以及上下文过长。Pi 的可读性来自把这些职责拆开，而不是假装它们不存在。

| 层次 | 负责什么 | 不应该偷偷负责什么 |
| --- | --- | --- |
| 模型适配 | 统一不同 Provider 的请求、流式事件和工具格式 | 不决定业务工具和产品交互 |
| Agent Loop | 驱动模型和工具往返，发出生命周期事件 | 不把所有产品策略写死在循环里 |
| Harness 工具 | 读写文件、执行命令并返回结构化结果 | 不让模型绕过参数和路径边界 |
| 会话与压缩 | 保存历史，在窗口不足时保持可继续工作 | 不把摘要当作无损历史 |
| TUI / SDK | 面向人或其他程序暴露能力 | 不成为底层 Agent 的反向依赖 |

## “没内置”不等于“做不到”

Pi 最值得学习的是扩展边界。计划模式、权限检查、状态栏、子 Agent 或自定义工具可以通过扩展实现，这带来两个结果：

1. 不需要的能力不会占据默认上下文、启动路径和维护成本。
2. 团队可以把自己的规则写成代码，而不是等待框架增加一个全局开关。

这和前端生态很像：Vite 提供插件钩子，但不会把每种构建策略都塞进核心。真正的判断不是“有没有功能”，而是“核心是否暴露了足够稳定的组合点”。

## 复杂度没有消失，只是变成了选择题

极简路线容易被误读成“系统越小越好”。实际上它做的是复杂度转移：

- 核心维护者少承担内置策略的兼容成本。
- 扩展作者需要自己处理生命周期、配置和冲突。
- 使用团队需要决定哪些安全能力必须安装，不能依赖默认值侥幸运行。

当团队规模变大、权限要求严格或会话需要集中治理时，统一控制面可能比自由扩展更重要。Pi 是理解 Harness 原语的好教材，不代表每个生产系统都应该复制它的产品边界。

## 阅读源码时抓住五条线

建议不要按目录从头翻到尾，而是沿五条问题链阅读固定版本：

1. `packages/agent/src/agent-loop.ts`：一次模型与工具循环如何结束、取消或继续？
2. `packages/coding-agent/src/core/tools/`：工具上下文和文件修改如何组织？
3. `packages/coding-agent/docs/sessions.md`：JSONL 会话、分支和恢复如何工作？
4. `packages/coding-agent/docs/compaction.md`：压缩后保留了哪些继续工作的条件？
5. `packages/coding-agent/src/core/extensions/`：扩展可以观察和改变哪些生命周期？

## 可以迁移到自己的项目

- 先定义最小闭环和稳定事件，再讨论功能清单。
- 把模型 Provider、Agent Loop、工具实现和 UI 分层，避免相互反向依赖。
- 新能力优先证明“为什么必须进入核心”；否则先做成可卸载扩展。
- 每个扩展都要定义加载、冲突、失败和清理行为。
- 安全能力不能因为“可扩展”就变成可选作业；生产环境必须给出默认基线。
- Project Trust 只控制本地资源是否加载，不是权限系统或沙箱；工具和扩展仍以当前进程用户权限运行。

## 读完后的自测

1. 如果把 TUI 换成 Web 页面，Agent Loop 哪些代码应该完全不动？
2. 计划模式适合进入核心，还是作为扩展？判断标准是什么？
3. 一个扩展覆盖了内置工具后，谁负责参数兼容、权限和回滚？
4. “核心很小”与“运行可靠”之间还缺哪些工程机制？
