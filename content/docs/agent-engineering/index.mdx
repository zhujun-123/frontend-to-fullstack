## 先把 Harness 说清楚

Coding Agent 不是“模型加一个终端”。模型只能根据当前输入决定下一步；把仓库规则、历史消息和工具说明送进去，把工具调用安全地执行，再把结果送回来的是 **Harness**。

一个能进入真实工作的 Harness 至少要持续回答五个问题：

1. **上下文**：模型这一轮应该看见什么，旧信息何时压缩？
2. **行动**：工具调用采用什么协议，结果如何与请求配对？
3. **边界**：哪些动作需要批准，执行后又被什么沙箱限制？
4. **状态**：会话、记忆、子任务和插件由谁持有，何时回收？
5. **证据**：失败、成本、重试和最终结果如何被观察与复核？

## 三个项目，三种取舍

这三份材料不适合合并成一篇“功能大全”。它们真正有价值的地方，是展示了三种不同的 Harness 设计重心。

| 路线 | 首要问题 | 核心做法 | 最值得学习的判断 |
| --- | --- | --- | --- |
| [Pi：极简内核](/docs/agent-engineering/pi-minimal-harness) | 怎样让 Agent 足够小，开发者能读懂并改造 | 模型适配、Agent Loop、工具和界面分层；缺失能力通过扩展补充 | 少做功能也可以是一种产品能力 |
| [Grok Build：生产控制面](/docs/agent-engineering/grok-production-harness) | 长时间执行时怎样控制风险、上下文和失败 | 工具协议、权限审批、OS 沙箱、压缩、记忆、成本和恢复 | Prompt 不能替代代码级不变量 |
| [DeepSeek Harness：可组合插件树](/docs/agent-engineering/dsh-composable-harness) | 复杂能力怎样替换、热重载并正确回收 | 命名服务、依赖调度、可逆副作用、Patch、Preset 与隔离 | 扩展性首先是生命周期问题 |

## 一条共同主线

三个项目看起来一个做减法、一个做完备控制、一个追求动态组合，但它们都没有把“模型更聪明”当作唯一答案。

- Pi 通过缩小内核，让系统更容易理解和替换。
- Grok Build 把不确定行为包进权限、协议、预算与恢复机制。
- DeepSeek Harness 把组件的注册、依赖和清理提升为框架能力。

因此阅读这个专栏时，不要只记项目名和 API。每一篇都要追问：**它维护了什么系统不变量，复杂度又被放到了哪里？**
