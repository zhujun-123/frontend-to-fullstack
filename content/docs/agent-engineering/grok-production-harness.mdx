## 一次任务经过哪些控制层

<Mermaid
  chart={`flowchart TB
    A[用户任务] --> B[静态 Prompt + 动态仓库上下文]
    B --> C[模型选择工具]
    C --> D[工具协议校验]
    D --> E{权限判定}
    E -->|拒绝| F[返回可解释错误]
    E -->|允许| G[OS 沙箱执行]
    G --> H[结构化工具结果]

    I --> B
    H --> J[成本 / 日志 / 恢复证据]`}
/>

这里最容易犯的错误，是把所有层都写进 System Prompt。例如要求模型“执行危险命令前先询问”，只能影响模型倾向，不能形成强制边界。真正的权限判定必须发生在工具执行之前，真正的资源限制必须发生在操作系统层。

## 六个必须由代码维护的不变量

### 1. 静态说明与动态现场分开

稳定的身份、行为规则适合保持静态；操作系统、Shell、当前目录、仓库规则和 Git 状态属于动态现场。分开后既能控制缓存前缀，也能对外部输入设置超时、长度和缺省行为。

### 2. 工具请求与结果必须配对

模型不是直接调用本地函数，而是通过协议提出请求。参数需要验证，流式执行最终必须产生明确的终态结果。上下文压缩也不能把工具请求和对应结果从中间切开，否则下一轮可能只看到“孤儿结果”。

### 3. 审批不等于沙箱

- **审批**回答：这个用户是否允许 Agent 执行本次动作？
- **沙箱**回答：即使动作开始执行，它最多能碰到哪些文件、进程和网络资源？

一个命令看起来只读，也可能通过参数、别名或外部驱动引入执行行为。因此安全分类需要看实际命令语义，不能只维护一张粗糙的命令名白名单。

### 4. 上下文压缩必须保住工作集

压缩不是把历史变短，而是让任务在丢失细节后仍能继续。需要保留当前目标、已完成修改、未解决问题、关键文件和工具调用关系，并明确摘要不是原始记录。

### 5. 成本不完整时不能伪装成完整

生产系统要区分“确实是零”和“这部分没有拿到”。如果某些调用缺少计费信息，总账必须标记为不完整，而不是给出一个看似精确但无法对账的数字。这条原则同样适用于 Token、耗时和子 Agent 汇总。

### 6. 失败必须有收口路径

重试需要预算，取消需要传播，父会话消失时子任务需要回收。模型陷入重复行为时可以检测并中止，但检测本身也可能误判，因此系统还需要定义预算耗尽后的最后行为。

## 长任务靠什么活下来

| 机制 | 解决的问题 | 不能解决的问题 |
| --- | --- | --- |
| Compaction | 当前窗口装不下全部历史 | 无损保留每个细节 |
| Memory | 跨会话找回稳定事实和经验 | 自动保证记忆永远正确、永不过期 |
| Subagent | 隔离专业任务的上下文与执行状态 | 免费并行；成本、取消和结果归并仍需治理 |
| Codebase Graph | 仓库变化后保持代码索引新鲜 | 替代真实源码、测试和运行证据 |
| Usage / Telemetry | 观察成本、失败和执行行为 | 默认收集所有敏感 Prompt、代码和路径 |

## 用在自己的 Agent 上

检查一个 Agent 是否接近生产可用，可以先问：

1. 工具参数在哪里校验，是否只有一个明确终态？
2. 权限批准和 OS 沙箱是否为两层独立防线？
3. 压缩后如何保证工具请求与结果不被拆散？
4. 取消能否从父任务传播到子任务和底层进程？
5. 成本与使用量缺失时，界面会不会制造假精确？
6. 日志和遥测默认是否避免泄露代码、Prompt、路径与凭据？

如果这些问题只能用“Prompt 已经要求模型注意”回答，系统仍停留在演示阶段。
